# Sam v0.7.0: Immutable Collections & Bounded Concurrency (DRAFT)

*Design document for v0.7.0. See `analysis_v0.7.0.md` and `PROPOSAL_v0.7.0.md` for the original exploration.*

> **Status (2026-11-26):**
> - **Milestone 1** (sequential `for`/`yield`) is implemented and merged.
> - **Milestone 2** (bounded concurrency) has its syntax and all semantic rules locked in this document. The worker-pool engine lives in `@sam-lang/runtime` (`sam.mapParallel` / `sam.forEachParallel`), not in generated flow code. No compiler or runtime changes are implemented yet.
> - **Milestone 2.2** (heterogeneous `parallel { ... }` block) is intentionally deferred to a separate change.

## Overview

| Milestone | Scope | Status |
| --- | --- | --- |
| M1 | `let xs = for x in items { yield ... }`, sequential | Done |
| M2 | `with { parallel: N, ordered: boolean }` on `for` loops | Design locked, implementation pending |
| M2.2 | Heterogeneous `parallel { ... }` fan-out | Deferred |

M2 adds concurrency to an existing `for` loop without changing sequential
behavior. A loop without a `with` block keeps the M1 semantics exactly.

---

## Chosen syntax

Ordered by default: the result preserves the iterable's original order.

```sam
let summaries = for part in chunks with { parallel: 3 } {
  let res = use Summarizer<Summary>(part)
  if (!res.ok) { return res }
  yield res.value
}
```

Unordered: values are appended as each worker finishes.

```sam
let summaries = for part in chunks with { parallel: 3, ordered: false } {
  let res = use Summarizer<Summary>(part)
  yield res.value
}
```

Dynamic concurrency limit: validated at runtime.

```sam
let summaries = for part in chunks with { parallel: workers } {
  yield Summarize(part)
}
```

Sequential (no `with` block): unchanged from M1.

```sam
let results = for item in data {
  yield transform(item)
}
```

- `parallel` accepts a positive integer literal or an expression. A literal is
  validated at compile time; a dynamic expression is validated at runtime.
- `ordered` is a boolean literal. It is only valid together with `parallel`.
  It defaults to `true`.
- `with` is a **contextual keyword**: it is only special immediately after the
  iterable expression in a `for` header. It does not become a global reserved
  word, so existing programs that use `with` as an identifier keep compiling.

## The five locked semantic rules

### 1. Error policy: `Result` values vs uncaught exceptions

An expected LLM or provider failure is **not** an exception. `use` returns
`Result<T, AgentError>`, and the worker returns that value to the user.

| Situation | Representation | Pool behavior |
| --- | --- | --- |
| HTTP error, timeout, retries exhausted, parse error, schema validation error | `{ ok: false, error }` | Normal completion. The pool does **not** abort. |
| Successful agent call | `{ ok: true, value }` | Normal completion. |
| Uncaught `throw` / rejected promise escaping the worker body | Exception | Abort the whole pool immediately and propagate the exception to the parent flow. |

The user decides what to do with an expected failure. Collect both successes
and failures as values:

```sam
let results = for part in chunks with { parallel: 3 } {
  let res = use Summarizer<Summary>(part)
  yield res
}
```

Or stop the flow on the first expected failure. This is a user choice, not
automatic pool behavior:

```sam
let values = for part in chunks with { parallel: 3 } {
  let res = use Summarizer<Summary>(part)
  if (!res.ok) { return res }
  yield res.value
}
```

An uncaught exception is a runtime/programming error, not a `Result`. It
aborts the pool and propagates immediately; it is never converted into a
`Result` by the concurrency layer.

### 2. `return <expr>` inside a parallel loop: cooperative cancellation

Returning from a worker aborts the whole parallel loop, not just that worker.

If the worker at index `2` executes `return res` while indices `0`, `1`, `3`
and `4` are still in flight:

1. The pool sets `aborted = true`.
2. It stops dispatching new items from the queue/iterator.
3. It calls `abort()` on the pool's `AbortController`, which is forwarded to
   active HTTP requests and to local runner processes. Local runners are
   killed immediately with `proc.kill()`.
4. It closes the source iterator (`iterator.return()`), so generators can
   release resources.
5. It discards results from the remaining in-flight workers.
6. The parent flow returns the early value **immediately**, without waiting
   for the stragglers.

Determinism when several workers return at almost the same time:

- The **first return that triggers the abort wins**.
- If more than one return is observed in the same tick, the worker with the
  **lowest original index wins**.
- All other return values and yielded values are discarded.
- Straggler rejections caused by the abort are swallowed (they are not
  unhandled rejections and are not surfaced to the parent flow).

`return` can return any expression, including a raw `Result` (`return res`) or
one of its fields (`return res.error`). The concurrency layer treats it as an
opaque value; it does not unwrap or validate it.

### 3. Ordering: `ordered: true` (default) vs `ordered: false`

#### `ordered: true` (default)

Each dispatched item gets a preassigned index. The worker writes to
`slots[index]`.

- If an iteration executes `continue`, or otherwise finishes without a
  `yield`, its slot is marked with the internal `SKIPPED` sentinel.
- If an iteration finishes with a `yield`, its slot holds the yielded value.
- After the pool settles, slots are compacted with
  `slots.filter(slot => slot !== SKIPPED)`. The result preserves the original
  relative order of the items that yielded, regardless of completion order.

`SKIPPED` is an internal `Symbol`, never a user-visible value, so it cannot
collide with yielded data.

#### `ordered: false`

Each worker appends its yielded value with `results.push(value)` as it
finishes. The final order is completion order and is intentionally
unspecified.

#### One value per iteration (confirmed)

The slot model assumes each iteration contributes **zero or one** yielded
value (`continue` = zero, `yield x` = one). This is confirmed for M2 and is
guaranteed by construction rather than by rejecting valid branching:

- In parallel mode, `yield x` compiles to `return { kind: "yield", value: x }`
  inside the per-iteration worker function.
- `continue` compiles to `return { kind: "continue" }`.
- A worker that reaches the end without yielding returns
  `{ kind: "continue" }` implicitly.
- `return x` compiles to `return { kind: "return", value: x }`.

Because `yield` returns from the worker, only one value can be emitted per
iteration. Multiple `yield` statements are allowed when they live in mutually
exclusive branches (`if` / `else`); any yield after the first executed one is
unreachable. The validator must not reject a body solely because it contains
two yield statements in different branches.

This keeps `ordered: true` deterministic and avoids interleaving multiple
values from one iteration with values from another.

### 4. Control-flow constraints

- **`break` is forbidden when its nearest enclosing loop is the parallel
  loop.** The validator must reject it with:

  ```text
  SemanticError: 'break' is not allowed inside a parallel 'for' loop.
  ```

  Sequential `for` loops keep allowing `break` exactly as in M1. A `break`
  inside a nested sequential loop in the worker body still targets that inner
  loop and remains allowed.

- **`continue` is allowed.** It means "this iteration contributes no value".
  In ordered mode it marks the slot as `SKIPPED`; in unordered mode it simply
  pushes nothing. It does not cancel other workers.

- **`parallel` validation.**
  - Literal `parallel: 0`, a negative number, a non-integer, or a non-number
    literal is a compile-time `SemanticError`.
  - A dynamic `parallel` expression is evaluated once, before dispatching any
    item. If it is not a positive integer, the pool throws a `RangeError`
    before starting any request. No partial work is dispatched. The exact
    runtime message is:

    ```text
    RangeError: 'parallel' concurrency limit must be a positive integer, received ${concurrency}.
    ```
  - If the concurrency limit exceeds the number of available items, the extra
    workers simply find the iterator exhausted.

- **`ordered` validation.**
  - `ordered` must be a boolean literal.
  - `ordered` without `parallel` is a `SemanticError`.
  - Unknown keys inside `with { ... }`, or an empty `with { }`, are
    `SemanticError`s.

- **Other flow rules are unchanged.** `return` is allowed; `yield` remains
  valid only inside a `for` expression; `break`/`continue` remain invalid
  outside a loop.

#### Nested parallel loops (allowed)

Nested parallel loops are allowed. Each `sam.mapParallel` /
`sam.forEachParallel` call owns its own pool state: concurrency limit, slots,
iterator, and `AbortController`. No mutable pool state is shared globally.

The outer worker's signal is passed to the inner call through its `signal`
option. If an outer worker returns, the outer abort propagates and cancels
inner pools, active requests, and local runner processes. A `return` from an
inner pool propagates through the outer worker as
`{ kind: "return", value }`.

### 5. Scope of `parallel { ... }` (heterogeneous fan-out)

**Decision: `parallel { ... }` is M2.2, not part of the M2 change.**

Rationale:

- M2 is about one mechanism: bounded concurrency over a homogeneous iterable.
- The heterogeneous block has different semantics (fixed named entries, no
  queue, no `yield`, no per-item index) and would expand the test surface.
- Mixing both in one PR makes cancellation and ordering rules harder to review.

Current status correction: the AST contains a `ParallelExpression` node, but
the parser and codegen do **not** implement the `parallel { ... }` block or
destructuring today. The earlier note that it "already works" was inaccurate.

Contract for M2.2 when it is implemented:

```sam
let result = parallel {
  sec: use Auditor<SecurityReport>(diff),
  perf: use Auditor<PerformanceReport>(diff)
}
```

- It runs the named entries with `Promise.all`.
- It returns an object whose fields are the individual `Result<T, E>` values;
  expected failures remain values and do not reject the block.
- The first version has **no early-return/cancellation semantics** beyond
  `Promise.all`; an uncaught exception rejects the block and propagates.
- No `yield` or flow statements inside the block; each field is an expression.
- Destructuring syntax (`let { sec, perf } = ...`) is part of the M2.2 design,
  not M2.

## AST changes

`ForStatementNode` gains the modifier fields:

```typescript
export interface ForStatementNode {
  type: "ForStatement";
  iterator: string;
  iterable: ExpressionNode;
  parallel?: ExpressionNode; // positive integer at runtime
  ordered?: boolean;         // literal only; default true
  body: StatementNode[];
}
```

`YieldStatement` stays a statement node, as decided in M1. `parallel` is an
`ExpressionNode` because dynamic values are allowed; `ordered` stays a boolean
literal.

---

## Parser changes

- After parsing the iterable expression, if the next token is the contextual
  identifier `with`, parse `{ key: value, ... }`.
- Accept `parallel` with an expression value.
- Accept `ordered` with a boolean literal.
- Reject duplicate keys and unknown keys with a clear `SemanticError`; an
  empty `with { }` block is also a `SemanticError`.
- Keep the existing `let <name> = for ...` and standalone `for ...` parsing
  paths unchanged.

---

## Validator changes

- Literal `parallel`: positive integer check (`SemanticError`).
- Dynamic `parallel`: no compile-time value check; runtime `RangeError`.
- `ordered` requires `parallel`; `ordered` must be a boolean literal.
- `break` inside a parallel loop: `SemanticError` with the exact message from
  rule 4.
- Multiple `yield` statements are allowed when control flow makes them
  mutually exclusive (for example, one in each branch of an `if` / `else`).
  The worker-return construction guarantees at most one emitted value per
  iteration; later yields are unreachable.
- Existing M1 checks remain: for-expressions require at least one `yield`,
  and `yield` is only valid inside a for-expression.

## Codegen design

Sequential loops keep the M1 code path. Parallel loops do **not** generate the
pool machinery inline. `generateFlow.ts` emits a declarative call to the
runtime, and `@sam-lang/runtime` owns the scheduler, cancellation, ordering,
and iterator handling.

### Runtime API

```typescript
type WorkerResult<R> =
  | { kind: "yield"; value: R }
  | { kind: "continue" }
  | { kind: "return"; value: unknown };

type MapParallelResult<R> =
  | { kind: "values"; values: R[] }
  | { kind: "return"; value: unknown };

sam.mapParallel<T, R>(
  iterable: Iterable<T>,
  options: { parallel: number; ordered: boolean; signal?: AbortSignal },
  worker: (item: T, signal: AbortSignal) => Promise<WorkerResult<R>>,
): Promise<MapParallelResult<R>>;

sam.forEachParallel<T>(
  iterable: Iterable<T>,
  options: { parallel: number; signal?: AbortSignal },
  worker: (item: T, signal: AbortSignal) => Promise<
    { kind: "continue" } | { kind: "return"; value: unknown }
  >,
): Promise<{ kind: "done" } | { kind: "return"; value: unknown }>;
```

`mapParallel` is for `for` expressions (`let xs = for ...`). `forEachParallel`
is for standalone parallel `for` statements that do not collect values.

### Generated code

Ordered (default):

```typescript
const _loop_summaries = await sam.mapParallel(
  chunks,
  { parallel: 3, ordered: true },
  async (part, signal) => {
    const res = await sam.use("Summarizer", part, SummarySchema, { signal });
    if (!res.ok) return { kind: "return", value: res };
    return { kind: "yield", value: res.value };
  },
);
if (_loop_summaries.kind === "return") return _loop_summaries.value;
const summaries = _loop_summaries.values;
```

Unordered uses `{ parallel: 3, ordered: false }`; the result is still
`{ kind: "values", values }`, but `values` is in completion order.

Standalone parallel loop:

```typescript
const _loop_result = await sam.forEachParallel(
  chunks,
  { parallel: 3 },
  async (part, signal) => {
    const finding = await sam.use("Auditor", part, FindingSchema, { signal });
    if (!finding.ok) return { kind: "return", value: finding };
    return { kind: "continue" };
  },
);
if (_loop_result.kind === "return") return _loop_result.value;
```

### Worker shape and signal propagation

- `yield x` compiles to `return { kind: "yield", value: x }` inside the worker.
- `continue` compiles to `return { kind: "continue" }`.
- The end of a worker body falls back to `{ kind: "continue" }`.
- Every `return x` inside the worker, including returns inside nested
  sequential loops, compiles to `{ kind: "return", value: x }`.
- The worker receives the pool's signal and passes it to every `sam.use` /
  `sam.useUnsafe` call in its body, including calls inside nested `if` blocks
  and nested sequential loops.
- A nested parallel loop passes the current worker signal through its
  `signal` option. The inner pool creates its own `AbortController` and
  forwards an outer abort to it.

### Runtime responsibilities

`mapParallel` and `forEachParallel` implement the rules in this document: the
shared iterator, the bounded dispatch loop, per-index slots, `SKIPPED`
compaction, first-return-wins arbitration, same-tick lowest-index tie-break,
immediate resolution on early return, iterator closing, and swallowing
straggler rejections.

`generateFlow.ts` must not emit `AbortController`, `while` loops, microtask
shims, or `iterator.return()` inline.

- `parallel` is evaluated once by the generated call and validated by the
  runtime before dispatch.
- An uncaught worker rejection aborts the pool and rejects the runtime call.
- An early return resolves the runtime call immediately with
  `{ kind: "return", value }`; remaining workers are aborted and discarded.

## Runtime changes required for M2

### Worker-pool engine

- Add `sam.mapParallel` and `sam.forEachParallel` to `@sam-lang/runtime` and
  to the `Runtime` type.
- Share one scheduler implementation. `mapParallel` adds slot accumulation and
  `ordered` handling; `forEachParallel` only schedules workers and ignores
  ordering.
- Each call owns its own `AbortController` and concurrency limit. A nested call
  receives the outer worker's signal through its `signal` option and links the
  two controllers; an outer abort cancels the inner pool.
- Validate `parallel` once, before dispatch. A non-positive or non-integer
  value throws the exact error from rule 4.

### Cancellation signal plumbing

- Add optional cancellation options to the runtime API:

  ```typescript
  sam.use(agent, prompt, schema, { signal })
  sam.useUnsafe(agent, prompt, { signal })
  ```

- Thread the signal through `executeAgent` into `providerExecute` and the
  local runner executor.
- In `providerExecute`, combine the pool signal with the existing per-agent
  timeout signal (`AbortSignal.any([timeout, pool])` or an equivalent guard).
  A request aborted because of an early return must not be reported as a
  user-visible timeout or provider error.
- For local runners (`claude`, `opencode`, `mock`), cancellation is immediate:
  call `proc.kill()` as soon as the signal aborts. There is no grace period;
  the worker result has already been discarded by an early return. Discard any
  output the process produced.

### Error policy in the pool

- Expected agent failures return `{ ok: false, error }` values and never abort
  the pool.
- An uncaught exception or unexpected rejection aborts the pool, closes the
  iterator, and rejects the `mapParallel` / `forEachParallel` call with the
  original error.

## Tests to add with the implementation

- Ordered default preserves input order despite reversed completion order.
- `ordered: false` reflects completion order.
- `continue` produces no value; ordered results are compacted correctly.
- `if` / `else` branches may each contain a `yield`; only one value is
  emitted per iteration because `yield` returns from the worker.
- `break` in a parallel loop is rejected at compile time.
- Literal `parallel: 0`, `-1`, `1.5`, and non-number values are rejected.
- Dynamic `parallel` values are checked at runtime before any request is
  dispatched, with the exact `RangeError` message.
- Early `return` aborts pending requests, stops dispatch, closes the
  iterator, and returns without waiting for stragglers.
- Two near-simultaneous returns: first wins; same-tick tie goes to the lowest
  index.
- Uncaught worker exceptions abort the pool and propagate.
- Abort signals reach the HTTP layer (fake `fetch` assertion).
- A parent return aborts nested parallel pools through the propagated signal.
- Local runner cancellation calls `proc.kill()` immediately.
- Generated code calls `sam.mapParallel` / `sam.forEachParallel` and contains
  no inline `AbortController`, dispatch `while` loop, or `iterator.return()`.
- Sequential `for` behavior and all M1 tests remain unchanged.
- One real run with a Groq model and `parallel: 2`, both ordered and unordered.
- CI on Linux, macOS, and Windows.

## Backward compatibility

- A `for` loop without `with { ... }` keeps the exact M1 sequential behavior.
- `break` keeps working in sequential loops.
- Existing programs that use `with` as a variable/identifier keep compiling
  because `with` is contextual.
- `parallel { ... }` remains unimplemented until M2.2; no existing program
  depends on it.
- M1's 213 tests remain the baseline. The current suite passes before any M2
  code is written.

## Decisions (closed)

Locked in this document:

- Syntax: `with { parallel: N, ordered: boolean }`.
- Expected agent failures are `Result` values; no automatic abort.
- Uncaught exceptions abort the pool and propagate.
- `return` triggers cooperative cancellation; first return wins; same-tick
  tie goes to the lowest index.
- `ordered: true` uses preassigned slots, `SKIPPED` markers, and final
  compaction; `ordered: false` pushes on completion.
- At most one value is emitted per iteration. Parallel `yield` compiles to a
  tagged worker return, so `if` / `else` branches may each contain a `yield`
  without violating the slot model.
- `break` is a `SemanticError` when its nearest loop is parallel; `continue`
  is allowed.
- Literal `parallel` is validated at compile time; dynamic `parallel` throws
  `RangeError` at runtime.
- `ordered` is a boolean literal only.
- Nested parallel loops are allowed with independent pools; the outer signal
  is propagated to inner pools.
- Local runners are killed immediately with `proc.kill()`; no grace period.
- The worker-pool engine lives in `@sam-lang/runtime` as `sam.mapParallel` /
  `sam.forEachParallel`, not inline in generated flow code.
- `parallel { ... }` is deferred to M2.2.

No semantic questions remain open. Implementation can proceed from this
document.
